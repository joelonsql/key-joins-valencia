% 4. It runs. Is it right?
% Rehearsal: equal share of 40:00 across 29 main slides; elapsed 04:08--05:31.
% Background: Establish the purpose without explaining the fanout or revealing
% FOR KEY syntax and diagnostics yet. "Key Joins are about writing joins whose
% intent is easier to read, and letting the database check that intent. That
% helps us catch query bugs during development." Invite the audience to consider
% the query, then show the PostgreSQL diagnostic on the next slide.
% Source attribution stays in notes because the thread title reveals the problem:
% Paul Jungwirth, "Avoiding double-counting in aggregates with more than one join?"
% https://www.postgresql.org/message-id/flat/86b9ec78-925c-1935-bc9d-6bad4ceb1f40@illuminatedcomputing.com
% Schema assumptions: orders.id is a primary key; both order_id columns are
% NOT NULL foreign keys to it, with enforced, non-deferrable constraints.
% For order 100, two items (25, 75) and two payments (40, 60) produce four
% intermediate rows. Both sums are 200 instead of the intended 100.
% The first FOR KEY join is valid. The second fails because o.id is no longer
% unique in the complete left operand. FOR KEY does not repair a query or prove
% the whole query correct. The standalone examples/key-joins-fanout.tex retains
% the input rows, complete diagnostic, and corrected aggregation queries.
% Omit the tentative BEAVER percentages from the recording: they awaited verification.
% Background (delivery): State the task: item totals and payment totals for each order.
% Give the audience a moment to look, then show the diagnostic. The optional
% fanout detour explains the rows and returns to Catching the query’s bug.
% Presenter notes:

% 23. What FOR KEY guarantees
% Appendix: optional material; no additional time beyond the 40-minute main schedule.
% Background: Recording 01:04:55–01:11:37. State the two result guarantees
% explicitly. "And these guarantees must hold for each join. We must check its
% complete inputs, including what earlier joins have done to them." A key join
% may be written with ON; FOR KEY requires the DBMS to verify the guarantees.
% The declared FK supplies the relationship. The three mathematical obligations
% on the complete operands remain useful background for questions:
% 1. All-non-null combinations of referenced-column values are unique.
% 2. Every all-non-null referencing-column combination has a matching referenced row.
% 3. The referencing columns are known not nullable, or the join type preserves
%    the referencing operand.
% Together they give exactly one output occurrence for every incoming referencing
% row, plus its unique matching referenced row for every all-non-null reference.
% An outer join may also emit referenced-only rows; do not promise equal total
% row counts for every join type. These guarantees concern the immediate result
% of each join, not a whole query's final SELECT, WHERE, or aggregation.
% Errors identify a missing relationship, uniqueness, match existence, or null
% preservation. Rejection means the conservative proof did not succeed, not that
% every possible dataset violates a condition. E0–E3 are not standardized codes.
% Mention the improved diagnostics and Christoph Berg's enthusiastic reaction
% as a recollection. The opening query's diagnostic appears in the main talk.
% Diagram: illustrate the completed feature with sample data. The displayed
% LEFT JOIN preserves the referencing table's total cardinality: four rows enter
% and four rows leave. Equal-height brackets exclude the headers. The blue arrows
% show the stronger guarantee that each particular row survives exactly once.
% Alice and Bob both acquire room (10,100); David acquires room (20,100).
% Carol has reserved at hotel 20 but has not yet been assigned a room.
% Her (20,NULL) finds no equality match; LEFT JOIN retains her reservation
% with NULLs in all ro.* columns. Room (10,101) contributes no result row.
% Schema assumptions for acceptance: rooms(hotel_id,room_number) is a primary
% key, and reservations(hotel_id,room_number) is an enforced, non-deferrable
